# 코드 품질 검토 결과

> 검토 대상: P117 구현 — 이용신청 → 이용안내 전환, 정원 제한 기능 추가

---

## 총평

전체 구조는 **양호**합니다. 특히 GAS 백엔드의 트랜잭션 설계와 락(Lock) 처리는 매우 견고합니다.
다만, 프론트엔드-백엔드 간 **검증 이중성**에서 놓쳐서는 안 될 취약점이 하나 확인되었고, 소수의 개선 포인트가 있습니다.

---

## ✅ 잘 짜여진 부분

### 1. 백엔드 Lock + Snapshot 구조 (40_Orders.gs)

`placeOrder` 함수는 `LockService.getScriptLock()`을 획득한 뒤 `orderRowsSnapshot`을 읽어 정원 카운팅을 수행합니다. 이 순서가 핵심입니다.

```
tryLock() → orderSheet.getDataRange() → 카운트 검증 → 쓰기
```

Lock을 먼저 잡고 그 안에서 스냅샷을 읽기 때문에, 동시 요청이 들어와도 **두 번째 요청은 첫 번째가 쓴 결과를 볼 수 있습니다.** Race condition 없음.

### 2. 트랜잭션 롤백 처리 (40_Orders.gs L671–706)

`PENDING → COMMITTED` 2단계 커밋 패턴이 구현되어 있고, 실패 시:
- 재고 원복 (stockValuesBefore 복원)
- 온기(크레딧) 환불 (refundCredit)
- 주문 상태 `FAILED` 마킹

3단계 롤백이 순서대로 try/catch로 감싸져 있어, 부분 실패 시에도 최대한 복구됩니다.

### 3. 멱등성(Idempotency) 처리

클라이언트는 `buildOrderAttemptSignature`로 서명을 계산하여 같은 주문 내용이면 같은 키를 재사용합니다. 서버는 `getExistingIdempotentOrderResult`로 이미 완료된 주문이면 동일 응답을 반환합니다. 네트워크 재시도로 인한 이중 주문을 방지하는 표준 패턴입니다.

### 4. 정원 카운팅 로직 (40_Orders.gs L411–436)

`todayOrderMap`을 `orderNo` 단위로 중복 제거하여 카운팅합니다. 한 주문에 간식이 여러 행인 경우에도 1건으로 올바르게 집계됩니다.

```javascript
// 한 orderNo의 deliveryType이 하나라도 'delivery'면 배달로 분류
if (!todayOrderMap[oNo]) {
  todayOrderMap[oNo] = (rDelType === 'delivery');
} else if (rDelType === 'delivery') {
  todayOrderMap[oNo] = true;
}
```

### 5. 프론트엔드 배달 마감 UI (confirm.js L93–140)

`applyDeliveryCapStatus()`는 페이지 로드 시 + 새 설정 조회 후 모두 호출되어 UI 상태를 동기화합니다. `btnDeliver.click` 이벤트에서도 `sessionStorage`를 재확인하여 마감 상태에서 배달 선택을 차단합니다 (L699).

## ⚠️ 취약점 및 개선이 필요한 부분

### [중요] 취약점 1: 배달 마감 후 클라이언트 우회 가능성

**위치:** `confirm.js` L697–710 (배달 버튼 클릭 핸들러)

현재 배달 버튼은 클릭 시 `sessionStorage.getItem('isDeliveryCapped')`를 확인합니다. 그런데 이 값은 **페이지 로드 시점**에 `guest.js`의 `loadSettings()`가 기록한 것입니다.

**시나리오:**  
1. 사용자 A가 `guest.html`에서 설정을 불러올 때 배달 1자리 남아 있음 → `isDeliveryCapped = false`  
2. 사용자 B가 먼저 배달 주문 완료 → 배달 마감  
3. 사용자 A는 `confirm.html`에서 `refreshConfirmGuestSettings()` 호출 전에 배달 버튼 클릭 가능  

`refreshConfirmGuestSettings()`는 비동기 호출이므로 실제 서버 값이 도착하기 전까지 UI가 이전 값을 보여줍니다. 다만, **최종 방어선은 서버(40_Orders.gs L447–452)에 있으므로 실제 이중 배달 접수는 발생하지 않습니다.** 클라이언트 우회는 프론트 UX 문제이지, 데이터 정합성 문제는 아닙니다.

**평가:** 서버에서 최종 검증하므로 데이터 무결성은 안전. 단, 사용자가 "배달 선택 → 주문 시도 → 서버 오류 응답" 경로를 겪을 수 있음.

### [개선] 취약점 2: `isCancel` 카운팅 조건 오류 가능성

**위치:** `40_Orders.gs` L421

```javascript
const isCancel = r[9] || (r.length > 9 && r[9] !== '');
```

이 두 조건은 동일한 `r[9]`를 검사합니다. `r[9] !== ''`은 `r[9]`가 truthy일 때 항상 참이므로, 오른쪽 조건은 실질적으로 의미가 없습니다. 취소 주문을 정원에서 제외하려는 의도인데, 실제로는 `isCommittedOrderRow(r, headers)` 필터가 앞(L416)에 있어서 이미 커밋된 행만 보기 때문에 실제 오작동은 없습니다. 하지만 코드 의도가 불명확합니다.

**권장:** 별도의 `cancelTimestamp` 컬럼 인덱스를 사용하는 것이 더 명확합니다.

---

### [개선] 취약점 3: `buildGuestSettingsResponse`의 이중 집계 비용

**위치:** `60_Settings.gs` L250–273

`getGuestSettings()`는 설정을 조회할 때마다 `getOrdersToday()`를 호출하여 오늘 주문을 전수 스캔합니다. `getOrdersToday`는 캐시된 값을 사용하지만, **캐시 무효화 직후 연속 호출 시 스프레드시트 2회 읽기**가 발생합니다.

일반적인 사용량에서는 문제 없지만, 운영 중 주문이 많아지면 응답 지연 가능성이 있습니다.

---

### [경미] 취약점 4: `confirm.js`의 `updateBill()` null 접근 가능성

**위치:** `confirm.js` L340

```javascript
const remainPoints = user.credit - totalPoints;
```

`user.credit`가 `undefined`이면 `NaN`이 되어 UI에 `NaN`이 표시됩니다. L616–624에서 초기화 로직이 있지만, 예외 경로에서 `user.credit`가 설정되지 않은 채 `updateBill()`이 호출될 수 있습니다.

**권장:** `const remainPoints = (user.credit ?? 0) - totalPoints;`

## 결론

코드는 **전반적으로 잘 짜여진 수준**입니다.

- **가장 중요한 부분** — 정원 초과 주문 차단 — 은 백엔드 Lock 내부에서 Snapshot 기반으로 안전하게 처리됩니다. 클라이언트가 마감 상태를 속이더라도 서버에서 막힙니다.
- 실제 수정이 **필요한 버그**는 없습니다. 발견된 사항들은 모두 가독성, 경계 방어, 성능 개선 영역입니다.
- 운영 규모(하루 5건 정도)에서는 성능 문제도 실질적으로 나타나지 않을 것입니다.
